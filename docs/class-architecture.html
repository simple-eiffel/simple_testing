Class Architecture: Complete Guide

The simple_testing framework consists of 7 core classes organized in a hierarchy. This guide explains each class, its purpose, how to use it, and how they work together.

1️⃣ TEST_SET_BASE (Deferred)

Base Class

🎯 Purpose

The base class that all test classes inherit from. Provides 40+ assertion methods for verifying expected behavior in tests.

📍 Location in Hierarchy

TEST_SET_BASE (inherits from EQA_TEST_SET)
    └─ Your test classes inherit from TEST_SET_BASE

🔧 How to Use

Step 1: Create your test class inheriting from TEST_SET_BASE:

class MY_TESTS
inherit TEST_SET_BASE
feature
    test_something
        do
            -- Your test logic here
        end
end

Step 2: Use assertion methods in your tests:

test_example
    do
        -- Boolean assertions
        assert ("condition_true", True)
        assert_true ("explicit_true", some_condition)

        -- Object assertions
        assert_attached ("obj_not_void", my_object)
        assert_equal ("values_equal", expected, actual)

        -- Numeric assertions
        assert_positive ("count_positive", my_list.count)
        assert_in_range ("value_in_range", value, 1, 100)

        -- String assertions
        assert_string_contains ("has_error", output, "ERROR")
        assert_string_starts_with ("http", url, "http://")

        -- Collection assertions
        assert_count_equals ("list_size", 5, my_list)
        assert_iterable_not_empty ("has_items", collection)
    end

📚 40+ Assertion Methods Available

Category Methods
Boolean assert, assert_true, assert_false
Object assert_attached, assert_void, assert_same_reference, assert_not_same_reference
Equality assert_equal, assert_not_equal
Integer assert_positive, assert_negative, assert_zero, assert_in_range, assert_greater_than, assert_less_than
Real assert_reals_equal (with epsilon), assert_real_in_range
String assert_string_contains, assert_string_starts_with, assert_string_ends_with, assert_string_empty, assert_string_length
Collection assert_count_equals, assert_iterable_empty, assert_iterable_not_empty, assert_array_has_item
Advanced NATURAL_64 assertions, epsilon comparisons for floating-point

⚠️ Common Mistakes

  • ❌ NOT inheriting from TEST_SET_BASE (inherit from it!)
  • ❌ Forgetting to prefix test methods with "test_" (required for test discovery)
  • ❌ Testing multiple things in one test (one assertion focus per test)
  • ✅ Use descriptive assertion tags: assert_equal ("user_name_matches", "john", user.name)

2️⃣ TEST_SET_BASE_EXTENDED (Deferred)

Extension Mixin

🎯 Purpose

Provides two extension points: Feature-level fixture hooks (on_prepare_feature, on_clean_feature) for per-test setup/cleanup, and nested fixture support (with_fixture) for scoped callback execution.

📍 Location in Hierarchy

TEST_SET_BASE_EXTENDED
    ├─ Deferred: on_prepare_feature
    ├─ Deferred: on_clean_feature
    └─ Deferred: with_fixture (callback: PROCEDURE)

🔧 How to Use - Feature-Level Hooks

Scenario: You need setup before each test and cleanup after each test. Database transaction example: 

class DATABASE_TESTS
inherit TEST_SET_BASE
    -- Optionally override on_prepare_feature / on_clean_feature if needed
feature
    on_prepare_feature
        -- Called before EACH test method
        do
            database.begin_transaction
        end

    on_clean_feature
        -- Called after EACH test method (even if exception thrown)
        do
            database.rollback  -- Undo changes from test
        end

    test_user_creation
        -- Runs with transaction active
        -- Changes will be rolled back after test
        do
            database.insert_user ("alice")
            assert ("user_created", database.user_exists ("alice"))
            -- on_clean_feature called here - transaction rolled back
        end

    test_user_deletion
        -- Also runs with fresh transaction
        do
            database.insert_user ("bob")
            database.delete_user ("bob")
            assert ("user_deleted", not database.user_exists ("bob"))
            -- on_clean_feature called here - transaction rolled back
        end
end

🔧 How to Use - Nested Fixtures (with_fixture)

Scenario: You need scoped fixture acquisition/release with LIFO (Last In, First Out) ordering. Perfect for nested resource management. 

test_with_nested_fixtures
    local
        l_test: FIXTURE_HOLDER
    do
        create l_test

        -- Nested fixture pattern with LIFO cleanup
        l_test.with_fixture (agent do
            -- Fixture 1 acquired
            database.begin_transaction

            l_test.with_fixture (agent do
                -- Fixture 2 acquired (nested inside Fixture 1)
                database.begin_savepoint ("sp1")

                -- Test logic here
                database.insert_user ("charlie")
                assert ("user_created", database.user_exists ("charlie"))

                -- Fixture 2 released (rollback to savepoint)
                database.rollback_to_savepoint ("sp1")
            end)

            -- Fixture 1 still active (transaction still open)
            -- Test verification here

            -- Fixture 1 released (transaction rolled back)
        end)

        -- Cleanup guaranteed even if exception thrown
        assert ("fixtures_cleaned", True)
    end

🔄 LIFO Cleanup Order

"Last In, First Out" means fixtures are released in reverse order of acquisition: 

with_fixture (acquire fixture 1)
    with_fixture (acquire fixture 2)
        with_fixture (acquire fixture 3)
            execute test
        release fixture 3  ← First released (innermost)
    release fixture 2     ← Second released
release fixture 1        ← Last released (outermost)

⚠️ Exception Safety Guarantee

Even if your test logic throws an exception, cleanup ALWAYS runs: 

test_exception_safe_cleanup
    local
        l_test: FIXTURE_HOLDER
    do
        create l_test
        l_test.with_fixture (agent do
            database.begin_transaction
            -- Even if this throws...
            if risky_operation_fails then
                throw_exception ("Operation failed")
            end
            -- ...cleanup STILL runs (transaction rolled back)
        end)
        -- Guaranteed: no transaction leaks even on error
    end

3️⃣ TEST_FIXTURE (Deferred)

Feature-Level Fixture Base

🎯 Purpose

Deferred base class for feature-level fixtures. Defines the lifecycle: on_create (setup) and on_destroy (cleanup). You create subclasses to add specific fixture behavior.

📍 Location in Hierarchy

TEST_FIXTURE (deferred)
    ├─ on_create: setup called before test
    ├─ on_destroy: cleanup called after test
    ├─ is_valid: status query
    └─ lifecycle_state: MML model query (0=invalid, 1=valid)

🔧 How to Use - Create Your Own Fixture

Scenario: You need fresh database state for each test. Create a fixture class: 

-- Your custom fixture class
class DATABASE_FIXTURE
inherit TEST_FIXTURE
    redefine
        on_create, on_destroy, is_valid
    end

feature
    valid_flag: BOOLEAN

    on_create
        -- Called once at test start (creates fresh state)
        do
            database.begin_transaction
            valid_flag := True
        ensure
            fixture_valid: is_valid
        end

    on_destroy
        -- Called once at test end (cleans up state)
        require
            fixture_valid: is_valid
        do
            database.rollback  -- Undo all test changes
            valid_flag := False
        ensure
            fixture_invalid: not is_valid
        end

    is_valid: BOOLEAN
        -- Returns True if fixture is in valid state
        do Result := valid_flag end
end

-- Now use it in your tests
class DATABASE_TESTS
inherit TEST_SET_BASE
feature
    test_user_creation
        local
            l_fixture: DATABASE_FIXTURE
        do
            -- Create fixture (fresh state)
            create l_fixture
            l_fixture.on_create

            -- Test logic with clean database
            database.insert_user ("alice")
            assert ("user_created", database.user_exists ("alice"))

            -- Cleanup (rollback all changes)
            l_fixture.on_destroy
            assert ("cleaned_up", not database.user_exists ("alice"))
        end
end

🔄 Fixture Lifecycle State Machine

┌──────────────┐
│    Invalid   │  (is_valid = False)
│ (no fixture) │
└──────────────┘
       ↓
   on_create() called
       ↓
┌──────────────┐
│    Valid     │  (is_valid = True)
│  (ready to   │
│    test)     │
└──────────────┘
       ↓
   on_destroy() called
       ↓
┌──────────────┐
│    Invalid   │  (is_valid = False)
│  (cleaned    │  (cleanup guaranteed)
│     up)      │
└──────────────┘

📋 Contracts: What's Guaranteed

Method Precondition Postcondition
on_create None (can be called anytime) is_valid = True (fixture ready)
on_destroy is_valid = True (fixture must be valid) is_valid = False (cleanup complete)

4️⃣ TEST_FIXTURE_MOCK (Concrete)

Mock Implementation

🎯 Purpose

Concrete implementation of TEST_FIXTURE for testing the fixture lifecycle itself. Shows how to properly implement a fixture. Used in test suite and as reference.

📍 When to Use

  • ✅ Testing fixture behavior (lifecycle, state transitions)
  • ✅ Reference implementation to understand how to create your own fixtures
  • ✅ Unit testing the framework itself
  • ❌ NOT for testing your actual application (create your own fixtures instead)

🔧 Example: Testing with TEST_FIXTURE_MOCK

test_fixture_lifecycle
    local
        l_fixture: TEST_FIXTURE_MOCK
    do
        -- Initially invalid
        create l_fixture
        assert ("initially_invalid", not l_fixture.is_valid)

        -- Create transitions to valid
        l_fixture.on_create
        assert ("after_create_valid", l_fixture.is_valid)

        -- Destroy transitions to invalid
        l_fixture.on_destroy
        assert ("after_destroy_invalid", not l_fixture.is_valid)
    end

test_fixture_model_query
    local
        l_fixture: TEST_FIXTURE_MOCK
    do
        create l_fixture

        -- Model query shows state as integer (0 or 1)
        assert_equal ("invalid_state_0", 0, l_fixture.lifecycle_state)

        l_fixture.on_create
        assert_equal ("valid_state_1", 1, l_fixture.lifecycle_state)

        l_fixture.on_destroy
        assert_equal ("invalid_state_0_again", 0, l_fixture.lifecycle_state)
    end

📚 Learn From TEST_FIXTURE_MOCK

When creating your own fixture, follow the TEST_FIXTURE_MOCK pattern:

            -- Your cleanup logic

5️⃣ FIXTURE_HOLDER (Concrete)

Nested Fixture Support

🎯 Purpose

Provides the with_fixture method for executing callbacks in scoped fixture contexts. Enables nested fixture patterns with automatic LIFO cleanup.

📍 When to Use

  • ✅ Need nested resource management (transactions within transactions)
  • ✅ Want LIFO cleanup guarantees
  • ✅ Testing scenarios that need exception-safe cleanup

🔧 How to Use FIXTURE_HOLDER

test_with_fixture_scoped_cleanup
    local
        l_holder: FIXTURE_HOLDER
    do
        create l_holder

        -- Execute code in fixture scope
        l_holder.with_fixture (agent do
            -- Setup happens automatically on entry
            database.begin_transaction

            -- Test code executes here
            database.insert_user ("dave")
            assert ("user_exists", database.user_exists ("dave"))

            -- Cleanup happens automatically on exit (even if exception)
            -- Transaction rolled back
        end)

        -- After exit: fixture cleaned up, transaction rolled back
    end

test_multiple_nested_fixtures
    local
        l_holder: FIXTURE_HOLDER
    do
        create l_holder

        -- Level 1: Outer fixture
        l_holder.with_fixture (agent do
            database.begin_transaction

            -- Level 2: Middle fixture (nested inside Level 1)
            l_holder.with_fixture (agent do
                database.begin_savepoint ("sp1")

                -- Level 3: Inner fixture (nested inside Level 2)
                l_holder.with_fixture (agent do
                    -- Deep nesting - innermost scope
                    database.insert_user ("eve")
                    assert ("user_created", database.user_exists ("eve"))
                end)
                -- Level 3 cleanup: no-op

                -- Level 2 still active - verify state
                assert ("user_still_exists_at_level_2", database.user_exists ("eve"))
            end)
            -- Level 2 cleanup: rollback to savepoint

            -- Level 1 still active
            assert ("user_deleted_by_savepoint", not database.user_exists ("eve"))
        end)
        -- Level 1 cleanup: rollback transaction
    end

⚠️ Exception Safety in with_fixture

test_exception_safe_with_fixture
    local
        l_holder: FIXTURE_HOLDER
    do
        create l_holder

        l_holder.with_fixture (agent do
            database.begin_transaction

            -- Even if code throws...
            if something_goes_wrong then
                throw_exception ("Error occurred")
            end

            -- ...cleanup STILL runs (guaranteed by postcondition)
        end)

        -- Guaranteed: transaction rolled back even on exception
    end

6️⃣ TEST_SYSTEM (Deferred)

System-Level Fixture Base

🎯 Purpose

Deferred base class for system-level fixtures that run once per entire test run (not per test). Perfect for expensive setup (database init, server startup).

📍 Location in Hierarchy

TEST_SYSTEM (deferred)
    ├─ on_prepare_test_system: called once at run start
    ├─ on_clean_test_system: called once at run end
    ├─ is_initialized: status query
    └─ initialization_state: MML model query (0=uninitialized, 1=initialized)

🔧 How to Use - Create System Fixture

Scenario: Database needs to be created once, used by all tests, then destroyed. 

-- Create once at test run start, destroyed once at end
class DATABASE_TEST_SYSTEM
inherit TEST_SYSTEM
    redefine
        on_prepare_test_system, on_clean_test_system, is_initialized
    end

feature
    initialized_flag: BOOLEAN

    on_prepare_test_system
        -- Called ONCE when test run STARTS
        require
            system_not_initialized: not is_initialized
        do
            -- Expensive one-time setup
            database.create_connection
            database.create_schema
            database.seed_data  -- Load test data
            initialized_flag := True
        ensure
            system_initialized: is_initialized
        end

    on_clean_test_system
        -- Called ONCE when test run ENDS
        require
            system_initialized: is_initialized
        do
            -- One-time cleanup
            database.drop_schema
            database.close_connection
            initialized_flag := False
        ensure
            system_cleaned: not is_initialized
        end

    is_initialized: BOOLEAN
        -- Query: is system ready?
        do Result := initialized_flag end
end

🎯 System vs Feature Lifecycle

TEST RUN START
    ↓
on_prepare_test_system (CALLED ONCE)
    Database created, schema created, test data loaded
    ↓
    [Now all 100 tests run, sharing same database]
    ↓
    test_1: uses database
    test_2: uses database (same database as test_1)
    test_3: uses database (same database)
    ...
    test_100: uses database
    ↓
on_clean_test_system (CALLED ONCE)
    Database destroyed, connection closed
    ↓
TEST RUN END

📋 Efficiency Advantage

Approach Cost When to Use
System Fixture
(once per run)		 1x expensive setup Database init (seconds per test run)
Feature Fixture
(once per test)		 100x setup cost Transaction isolation (milliseconds per test)

-- 1. SYSTEM FIXTURE (runs once per test run)
class APP_TEST_SYSTEM
inherit TEST_SYSTEM
feature
    initialized_flag: BOOLEAN

    on_prepare_test_system
        do
            create database.make
            database.connect ("test_db")
            database.create_schema
            initialized_flag := True
        ensure
            system_initialized: is_initialized
        end

    on_clean_test_system
        do
            database.drop_schema
            database.close
            initialized_flag := False
        ensure
            system_cleaned: not is_initialized
        end

    is_initialized: BOOLEAN
        do Result := initialized_flag end
end

class TRANSACTION_FIXTURE
inherit TEST_FIXTURE
feature
    valid_flag: BOOLEAN

    on_create
        do
            database.begin_transaction
            valid_flag := True
        ensure
            fixture_valid: is_valid
        end

    on_destroy

            database.rollback
            valid_flag := False

-- 3. TEST CLASS (uses fixtures and assertions)
class USER_TESTS
inherit TEST_SET_BASE
feature
    test_user_creation
        local
            l_fixture: TRANSACTION_FIXTURE
        do
            -- Feature-level fixture: fresh transaction
            create l_fixture
            l_fixture.on_create

            -- Test assertions (40+ available)
            database.create_user ("alice", "alice@example.com")
            assert_true ("user_created", database.user_exists ("alice"))
            assert_equal ("email_correct", "alice@example.com", database.get_user_email ("alice"))

            -- Cleanup
            l_fixture.on_destroy  -- Rolls back transaction
        end

    test_user_deletion
        local
            l_fixture: TRANSACTION_FIXTURE
            l_holder: FIXTURE_HOLDER
        do
            -- Feature-level fixture: fresh transaction
            create l_fixture
            l_fixture.on_create

            database.create_user ("bob", "bob@example.com")

            -- Nested fixture: savepoint within transaction
            create l_holder
            l_holder.with_fixture (agent do
                database.begin_savepoint ("sp1")
                database.delete_user ("bob")
                assert_false ("user_deleted_in_scope", database.user_exists ("bob"))
                database.rollback_to_savepoint ("sp1")
            end)

            -- Back to transaction level
            assert_true ("user_restored_from_savepoint", database.user_exists ("bob"))

            l_fixture.on_destroy  -- Rolls back entire transaction
        end
end

🎯 Design Decisions

  • USE TEST_SYSTEM FOR: One-time expensive setup (seconds per run)
    • Database initialization
    • Server startup
    • Loading large seed datasets
  • USE TEST_FIXTURE FOR: Per-test isolation (milliseconds per test)
    • Transaction per test
    • Fresh resource allocation
    • Test-specific setup/cleanup
  • USE WITH_FIXTURE FOR: Nested scoped cleanup (LIFO)
    • Savepoint within transaction
    • Resource nesting
    • Callback-based fixture patterns
